# Corpus propre — exploitation d'un front sur la plateforme développeur de Cloudflare (checklist)

Constitué le 28/10/2026 pour la fiche `expert-ops-cloudflare`, après la baseline de
`fixtures/fixture-ops-cloudflare.md` (figée à 10:41, commit 6740645). Borné aux 3 verbes de
forge-ops (déployer, exploiter, restaurer) sur un front et son API servis par **Workers** avec
assets statiques, ou par **Pages** quand le projet existe déjà. Chaque point cite la page officielle
qui le fonde, lue le 28/10/2026 entre 10:44 et 10:51 par `curl -sL` (version Markdown servie par
developers.cloudflare.com), avec la date de mise à jour que la page affiche ; rien n'y est écrit de
mémoire. Les faits « mesurés au pilot » viennent de `references/INTEGRATIONS-FOURNISSEURS.md` de
digit-ai-factory, section Cloudflare, mesures du 25/08/2026 (TF-0611 à TF-0613) : relus le
28/10/2026, ils ne sont pas dans la documentation et se rejouent par la commande qu'ils citent.

1. **Voie par défaut : Workers ; Pages est une voie existante à migrer** — la page Pages ouvre sur
   « Workers supports most Pages use cases and offers a broader feature set. It is Cloudflare's
   primary platform for building applications. Start new projects with Workers. » Le guide de
   migration : « Unless otherwise stated below, what works in Pages works in Workers » ; sa matrice
   marque absents de Pages les déploiements progressifs, les routes partielles (« Non-root routes »)
   et Workers Logs. Pages n'est pas déclaré déprécié : le mot « deprecated » n'apparaît dans aucune
   des deux pages (0 occurrence, recompté le 28/10/2026). Un projet Pages existant se migre par le
   guide ; Pages ne se prescrit pas à un projet neuf. Sources :
   https://developers.cloudflare.com/pages/ (mise à jour du 25/08/2026) ;
   https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/ (12/10/2026)
2. **Les deux voies à ne jamais prescrire** — Workers Sites : « It has been deprecated in Wrangler
   v4 […] Do not use Workers Sites for new projects » ; la clé `site` de la configuration Wrangler
   est marquée « deprecated ». Firewall Rules : « Cloudflare Firewall Rules has been deprecated.
   Cloudflare has moved existing firewall rules to WAF custom rules ». Sources :
   https://developers.cloudflare.com/workers/configuration/sites/ (23/04/2026) ;
   https://developers.cloudflare.com/firewall/ (14/08/2026) ;
   https://developers.cloudflare.com/waf/custom-rules/ (16/10/2026) ;
   https://developers.cloudflare.com/workers/wrangler/configuration/ (27/10/2026)
3. **Configuration minimale et service des assets** — fichier `wrangler.jsonc`, `wrangler.json` ou
   `wrangler.toml`, deux champs obligatoires : `name` et `compatibility_date`. `assets.directory`
   remplace le dossier de sortie de Pages ; le mode SPA ou 404 n'est plus deviné (« this behavior is
   explicit and must be set up manually ») : `not_found_handling = "single-page-application"` ou
   `"404-page"`. Workers sert les assets avant le script sauf `assets.run_worker_first` (`true`, ou
   tableau de motifs, 100 entrées au plus). En mode SPA, avec une date de compatibilité au
   2025-04-01 ou après, une requête de navigation (`Sec-Fetch-Mode: navigate`) n'invoque pas le
   script : ouvrir `/api/…` dans un navigateur rend le HTML, sauf motif `run_worker_first`.
   `.assetsignore` retient un fichier du dossier d'assets. Sources : guide de migration ;
   https://developers.cloudflare.com/workers/static-assets/binding/ (12/10/2026) ;
   https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/ (12/10/2026)
4. **`_headers` et `_redirects` : ce qu'ils couvrent** — pris en charge nativement, dans le dossier
   des assets. `_headers` : « not applied to responses generated by your Worker code » (SSR,
   `run_worker_first`, API) ; 100 règles, 2 000 caractères par ligne ; les redirections passent
   avant les en-têtes. `_redirects` : pas appliqué aux réponses du Worker ; 2 000 redirections
   statiques et 100 dynamiques, 1 000 caractères par déclaration, code 302 par défaut ; les
   **redirections de niveau domaine ne sont pas prises en charge** (`www` vers l'apex, par exemple).
   Un domaine personnalisé exige un nom exact : `www` et l'apex se relient par une règle de
   redirection de zone et un enregistrement **proxifié** pour l'hôte de départ (`A` vers `192.0.2.0`
   ou `AAAA` vers `100::`). Mesuré au pilot : Cloudflare ne termine le TLS que pour un hôte proxifié,
   sans lui la redirection ne se déclenche jamais. Sources :
   https://developers.cloudflare.com/workers/static-assets/headers/ (22/09/2026) ;
   https://developers.cloudflare.com/workers/static-assets/redirects/ (25/08/2026) ;
   https://developers.cloudflare.com/workers/configuration/routing/custom-domains/ (29/09/2026)
5. **Environnements et bindings : rien n'est hérité, et un identifiant oublié crée une ressource**
   — un environnement crée un Worker distinct nommé `<nom>-<environnement>` ; les bindings (`vars`,
   `kv_namespaces`, `r2_buckets`, `d1_databases`…) et les secrets « must be specified per
   environment ». Provisionnement automatique : un binding déclaré **sans identifiant** fait créer la
   ressource au `wrangler deploy` (KV, R2 et D1 notamment), préfixée du nom du Worker. Conséquence
   déduite de ce mécanisme, non mesurée : un `database_id` oublié dans `[env.production]` donne une
   base neuve et vide, pas une erreur. Migrations D1 : la page conseille le nom de la base plutôt que
   celui du binding, « to avoid accidentally running migrations on the wrong binding ». Hyperdrive
   relie un Worker à un Postgres existant, Supabase compris ; la page d'intégration Supabase de
   Cloudflare fait encore poser la clé `anon`, dépréciée côté Supabase : suivre le corpus
   `ops-supabase` §2. Sources : https://developers.cloudflare.com/workers/wrangler/environments/ (18/10/2026) ;
   https://developers.cloudflare.com/workers/wrangler/configuration/ (27/10/2026) ;
   https://developers.cloudflare.com/d1/reference/migrations/ (08/06/2026) ;
   https://developers.cloudflare.com/workers/databases/third-party-integrations/supabase/ (23/04/2026) ;
   https://developers.cloudflare.com/hyperdrive/ (21/10/2026)
6. **Secrets et `.dev.vars`** — « Do not use `vars` to store sensitive information ».
   `wrangler secret put <KEY> --env <env>` **crée une version et la déploie immédiatement** ;
   `wrangler versions secret put` crée seulement la version, mise en service ensuite par
   `wrangler versions deploy`. `secrets.required` fait échouer `wrangler deploy` et
   `wrangler versions upload` si un secret listé manque, et la clé `secrets` figure parmi les clés
   non héritées : elle se déclare dans chaque environnement. `--secrets-file` téléverse secrets et code
   ensemble, et les secrets absents du fichier sont conservés. En local, `.dev.vars` ou `.env` (pas
   les deux), `.dev.vars.<environnement>` par environnement : « Add `.dev.vars*` and `.env*` to your
   project's `.gitignore` file ». Sources :
   https://developers.cloudflare.com/workers/configuration/secrets/ (15/10/2026) ;
   https://developers.cloudflare.com/workers/wrangler/commands/workers/ (26/10/2026)
7. **Versions : séparer le téléversement de la mise en service** — une version capture code, assets,
   bindings et réglages de compatibilité ; « State changes for associated storage resources such as
   KV, R2, Durable Objects, and D1 are not tracked with versions. » `wrangler deploy` crée et déploie
   à 100 % d'un coup ; `wrangler versions upload` téléverse sans déployer, mais le tout premier
   téléversement d'un Worker exige `wrangler deploy` ; mise en service par
   `wrangler versions deploy <id>@<p>% <id>@<p>% -y` ; routes et domaines changent par
   `wrangler triggers deploy`, pas par `versions upload`. Wrangler affiche les 100 dernières
   versions, et l'on ne déploie ni ne revient qu'à l'une d'elles.
   Sources : https://developers.cloudflare.com/workers/versions-and-deployments/ (22/09/2026) ;
   https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/ (15/07/2026) ;
   https://developers.cloudflare.com/workers/wrangler/commands/workers/ (26/10/2026)
8. **Déploiement progressif et décalage de version** — deux versions au plus par déploiement, chaque
   requête tirée au sort selon les pourcentages. « Version affinity is particularly important when
   your Worker serves static assets with content-hashed filenames » : sans elle, le HTML d'une
   version demande un `assets/index-<empreinte>.js` que l'autre n'a pas, d'où un 404 et une page
   cassée. La clé `Cloudflare-Workers-Version-Key` se pose par une Transform Rule de la zone,
   indisponible sur `*.workers.dev`. Essai avant tout trafic : nouvelle version à 0 %, puis
   l'en-tête `Cloudflare-Workers-Version-Overrides: <worker>="<id>"`. Absent de Pages. Sources :
   https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/ (18/10/2026) ;
   https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/version-affinity/ (03/07/2026) ;
   https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/ (03/07/2026)
9. **Retour arrière : ce qu'il restaure, ce qu'il ne restaure pas** — `wrangler rollback
   [<VERSION_ID>] --message "<motif>"` crée sur-le-champ un déploiement à 100 % ; sans identifiant,
   il vise « the version uploaded before the latest version », qui n'est pas forcément la dernière
   version saine ; la page de la commande liste `--name` et ne liste pas `--env`. « Resources
   connected to your Worker will not be changed during a rollback » ; il est refusé si la version
   visée lie un bucket R2, un espace KV ou une file supprimés, ou après un changement de cycle de vie
   d'un Durable Object ; 100 dernières versions. Secrets : aucune page lue ne dit ce qu'un retour
   arrière en fait ; une version capture ses bindings et « Secrets are a type of binding », donc le
   retour arrière ramène probablement la valeur de la version visée : à vérifier sur la
   préproduction avant de révoquer une ancienne clé. Pages : retour arrière vers un déploiement de
   production seulement, « preview deployments are not valid rollback targets ». Sources :
   https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/ (15/07/2026) ;
   https://developers.cloudflare.com/workers/wrangler/commands/workers/ (26/10/2026) ;
   https://developers.cloudflare.com/pages/configuration/rollbacks/ (21/04/2026)
10. **Données D1 : Time Travel, et un export qui bloque** — Time Travel est toujours actif :
    restauration à la minute sur 30 jours (offre Workers payante) ou 7 jours (gratuite), sans coût.
    `wrangler d1 time-travel info <BASE>` rend le signet courant, à noter avant une migration ;
    `wrangler d1 time-travel restore <BASE> --bookmark=<signet>` « is a destructive operation, and
    overwrites the database in place », annule les requêtes en vol et rend le signet qui l'annule.
    `wrangler d1 export` : « A running export will block other database requests ».
    `wrangler d1 migrations apply` : une migration en erreur est annulée, la précédente reste
    appliquée. R2 et KV n'ont aucun retour arrière par version (point 7). Sources :
    https://developers.cloudflare.com/d1/reference/time-travel/ (21/04/2026) ;
    https://developers.cloudflare.com/d1/best-practices/import-export-data/ (21/04/2026) ;
    https://developers.cloudflare.com/workers/wrangler/commands/d1/ (23/04/2026)
11. **Domaines et routes : les serveurs de noms décident de la plateforme** — « Unlike Pages, Workers
    does not support any domain whose nameservers are not managed by Cloudflare » ; la matrice
    marque « Custom domains outside Cloudflare zones » absent de Workers et présent dans Pages. Un
    domaine personnalisé exige une zone Cloudflare active ; « You cannot create a Custom Domain on a
    hostname with an existing CNAME DNS record » ; ni joker, ni autre nom que l'hôte exact. Une
    route (`example.com/foo/*`) sert une partie des chemins, ce que Pages ne sait pas faire. Mesuré
    au pilot : le scan DNS automatique a importé **zéro** enregistrement sur quatre zones ajoutées
    par API, 47 manquants dont 12 `MX`, 4 SPF, 2 DKIM et 3 `SRV`, sans erreur ni avertissement ;
    aucun `MX`, `SRV`, `CNAME` de messagerie ni DKIM ne doit être proxifié. L'ordre de la bascule et ses
    contrôles vivent chez forge-ops : `references/GESTES-EXPLOITATION.md`, section G-03, et
    `scripts/verifier-migration-dns.mjs`, `--diff` pour les manques et `--proxifies` pour la
    messagerie proxifiée (existence et options vérifiées le 28/10/2026). Sources :
    guide de migration ; page des domaines personnalisés ;
    https://developers.cloudflare.com/workers/configuration/routing/routes/ (18/10/2026)
12. **`workers.dev`, Version URLs et Access devant la préproduction** — `workers.dev` est public quand
    il est actif ; « Disabling your workers.dev route does not disable Version URLs, Preview URLs, or
    Deployment URLs » ; une désactivation faite au seul tableau de bord revient au `wrangler deploy`
    suivant. Les Version URLs (clé `preview_urls`) suivent `workers_dev` par défaut. Access exige Zero Trust
    activé sur le compte et le droit de gérer Workers et applications Access. Protéger **le Worker**
    (« Protect one Worker ») couvre ses routes, domaines personnalisés, `workers.dev` et
    prévisualisations ; une application Access par nom d'hôte ne protège que cette URL. L'écran
    Workers propose deux politiques, membres du compte ou domaine de courriel ; une liste nominative
    n'est ni l'une ni l'autre et se pose dans l'application Access de Zero Trust, où la page renvoie
    toute configuration avancée. Sources :
    https://developers.cloudflare.com/workers/configuration/routing/workers-dev/ (22/09/2026) ;
    https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/ (22/09/2026) ;
    https://developers.cloudflare.com/workers/configuration/cloudflare-access/ (12/10/2026)
13. **Jetons et identifiants : CI, poste, dépôt** — CI : jeton d'API du modèle « Edit Cloudflare
    Workers », restreint au compte et aux zones du projet, avec `CLOUDFLARE_ACCOUNT_ID` ; « Don't
    store the value of `CLOUDFLARE_API_TOKEN` in your repository ». Ce modèle accorde huit
    permissions, dont Workers Routes, Workers Scripts, Workers KV Storage, Workers R2 Storage et
    Workers Tail, et **aucune sur D1** : `d1 migrations apply --remote` en CI exige d'ajouter
    « D1 Edit » (la même page l'écrit aussi « D1 Write »). Une règle de redirection de zone relève de
    « Single Redirect Edit ». Mesuré au pilot : sous « Page Rules: Edit », les Single Redirects ont été refusés
    (`10000 Authentication error`) ; il n'existe pas de permission « Account → Zone → Create »,
    la création de zone passe par `Zone:Zone:Edit`. Poste : `wrangler login` prend toutes les
    portées par défaut et range le jeton OAuth en clair dans
    `~/.config/.wrangler/config/default.toml`, sauf `--use-keyring` ; `CLOUDFLARE_API_TOKEN` prime
    sur ce jeton. Dépôt : `.dev.vars*`, `.env*` et `.wrangler/state` (« should be added to your
    `.gitignore` »). Sources :
    https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/ (18/10/2026) ;
    https://developers.cloudflare.com/fundamentals/api/reference/template/ (20/04/2026) ;
    https://developers.cloudflare.com/fundamentals/api/reference/permissions/ (12/10/2026) ;
    https://developers.cloudflare.com/workers/wrangler/commands/general/ (02/09/2026) ;
    https://developers.cloudflare.com/workers/local-development/local-data/ (25/06/2026)

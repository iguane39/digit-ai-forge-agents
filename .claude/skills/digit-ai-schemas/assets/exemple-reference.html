Pourquoi des agent pools Linux et pas Windows ?

Les pipelines Azure DevOps de l'orchestrateur tournent sur des agent pools auto-hébergés Linux (Ubuntu LTS). Ce choix se justifie par trois raisons :

  • Compatibilité native avec l'outillage du parcours : Docker (build des images), Terraform, checkov, bandit, Cosign, Azure CLI, jq, kubectl, Promptfoo, RAGAS sont tous des outils Unix-first. Sur Linux, les commandes shell tournent telles quelles dans les YAML.
  • Coût et performance : un agent Linux consomme ~30% moins de RAM et CPU qu'un agent Windows équivalent, et le démarrage des conteneurs est nettement plus rapide. À volume de pipelines élevé (plusieurs centaines de runs/mois), l'économie cumulée est sensible.
  • Adéquation avec le runtime cible : les Container Apps Digit-AI tournent sur des images Linux (Python, Node.js, ces stacks ne sont pas Windows-first). Builder sur Linux dans les pipelines garantit une parité parfaite entre l'environnement de build et l'environnement d'exécution.

Un agent Windows serait justifié uniquement si un POC utilisait du .NET Framework legacy (avant .NET Core / .NET 8). Ce n'est le cas d'aucun des POCs en cours dans le portfolio IA Digit-AI. Si ce cas survenait, un pool Windows secondaire pourrait être ajouté pour ce POC précis sans remettre en cause le défaut Linux.

Mission 1

Récupération du POC · composants techniques

Palier 1

Objectif et fonctionnement

Quand un Product Owner Squad estime que son POC est suffisamment mature pour entrer dans le parcours d'industrialisation, il pose un tag vX.Y.Z-poc sur son repo. Cet acte simple est le point d'entrée unique du parcours POC-to-Prod : il déclenche la prise en charge automatique du POC par l'Agent IA.

La Mission 1 commence par cloner le repo, puis elle cartographie automatiquement ce qu'elle y trouve : quel langage est utilisé (Python, Node, autre), quelles dépendances sont importées, quels modèles IA sont appelés, quel manifest Terraform décrit l'infrastructure cible, quelles evals (tests qualité IA) sont déjà présentes. Cette cartographie est packagée dans un fichier JSON appelé contexte du POC, qui devient l'entrée standardisée des missions suivantes.

L'objectif est de transformer la diversité des POCs (chaque Squad a ses habitudes) en un format pivot unique que toutes les missions aval comprennent. Sans cette uniformisation, chaque mission devrait s'adapter à chaque POC : impossible à industrialiser.

Mission 2

Audit du POC contre les Standards · composants techniques

Palier 1 (Light) Palier 2 (Complet)

Objectif et fonctionnement

Une fois le POC cartographié par M1, il faut mesurer son écart aux Standards Digit-AI. Les Standards sont la formalisation écrite de ce qu'une application doit respecter pour rentrer dans le parcours d'industrialisation. Il y a deux niveaux : un Standard Light (10 vérifications essentielles, principalement sur la sécurité de base et la signature des images) et un Standard Complet (20 chapitres couvrant tous les aspects : observabilité, FinOps, PRA, gestion des secrets, etc.).

La Mission 2 exécute mécaniquement chaque vérification contre le code du POC. Elle produit deux livrables : un rapport HTML autonome lisible par un humain (avec les écarts classés par sévérité : bloquant, important, conseillé) et un JSON structuré machine-lisible qui alimente le dashboard portfolio.

Le Standard Light est exécuté en premier (Palier 1). S'il est franchi, la promotion vers DEV MVP devient possible. Le Standard Complet est exécuté ensuite (Palier 2), avec un seuil de tolérance plus haut puisqu'on attend que la Mission 4 corrige les écarts plutôt que de bloquer.

L'enjeu pédagogique de cette mission : rendre la conformité observable et chiffrée. Avant l'orchestrateur, la conformité d'un POC était une opinion d'expert ; après, c'est un score reproductible.

Mission 3

Déploiement DEV MVP et baseline SLI · composants techniques

Palier 1 (manuel) Palier 2 (auto)

Objectif et fonctionnement

La Mission 3 est le premier passage du POC dans l'environnement DSI gouverné. Jusqu'ici, le POC tournait dans la Sandbox ou en DEV POC sous la responsabilité de la Squad. Maintenant, l'orchestrateur le prend en charge dans un environnement qui ressemble à la PROD : sous Standard Complet, intégré au réseau hub-and-spoke Digit-AI, avec les briques régaliennes activées.

Cette mission fait plusieurs choses en chaîne :

  1. Crée le repo prod-{nom} dans l'organisation Azure DevOps DSI (s'il n'existe pas) et y importe le code du POC. Ce repo devient la source de vérité du code en production, avec des branch policies strictes.
  2. Builde l'image Docker à partir du code : compilation, exécution des analyses statiques (SAST = Static Application Security Testing) pour détecter les bugs sécurité, scan des dépendances pour détecter les bibliothèques vulnérables, génération du SBOM (liste exhaustive des bibliothèques pour la traçabilité).
  3. Signe l'image avec Cosign. La signature est cryptographique et attachée au digest de l'image. C'est la garantie que cette image-là, et pas une autre, sera déployée jusqu'en PROD.
  4. Pousse l'image dans l'ACR DSI avec le tag vX.Y.Z-mvp.
  5. Provisionne le RG DEV MVP via Terraform : crée le Container App, le Key Vault, l'Application Insights, branche les peering hub, applique les Azure Policies.
  6. Déploie le Container App avec l'image vX.Y.Z-mvp.
  7. Établit la baseline SLI sur 7 jours : laisse l'application tourner avec un trafic de test puis enregistre les métriques de référence (latence P95, taux d'erreur, throughput). Cette baseline devient la référence pour la Mission 4 et pour les contrôles SLI ultérieurs en PROD.

L'enjeu pédagogique : passer d'un POC artisanal à un build industriel reproductible. À partir de cette mission, plus rien n'est artisanal : chaque action est journalisée, l'image est signée, l'infrastructure est codifiée.

Mission 4

Remédiation assistée sur observation · composants techniques

Palier 2 (règles) Palier 3 (LLM)

Objectif et fonctionnement

La Mission 2 a produit un rapport d'audit listant les écarts au Standard. Plutôt que de rejeter le POC tant qu'un humain n'a pas corrigé manuellement chaque écart (lent, sujet à erreur), la Mission 4 génère elle-même les corrections sous forme de Pull Requests qu'il suffit à la Squad et au Run d'examiner puis de fusionner.

Concrètement, M4 prend deux entrées :

  • Le rapport d'audit M2 (la liste des écarts à corriger)
  • Les observations DEV MVP issues de M3 (couverture de tests, baseline SLI, comportements observés)

Pour chaque écart, M4 décide d'une stratégie de remédiation. Deux moteurs cohabitent selon le palier de maturité de l'orchestrateur :

  • Palier 2 — moteur à règles déterministes (script Python conteneurisé). Il sait corriger les écarts courants : ajouter un tag FinOps manquant, activer une managed identity, ajouter un Private Endpoint, remonter une version de SKU, etc. Ce moteur couvre environ 70% des cas réels, qui sont des écarts mécaniques.
  • Palier 3 — appel à un LLM hébergé dans Azure AI Foundry pour les patches non-triviaux : refactoring d'une stack d'observabilité, restructuration des secrets, mise en conformité d'un schéma de logs custom. C'est là que la valeur "IA" de l'orchestrateur s'exprime pleinement.

Chaque patch généré aboutit dans une Pull Request étiquetée par le chapitre du Standard auquel elle se rattache. La PR contient le diff exact, un commentaire explicatif, et un lien vers la règle du Standard violée. La review est co-obligatoire : un Run engineer ET un dev Squad doivent approuver avant le merge. À chaque merge, le pipeline M3 est rejoué pour vérifier que l'application reste fonctionnelle.

L'enjeu pédagogique : passer d'une remédiation manuelle qui prend des semaines à une remédiation assistée qui prend des heures, sans abandonner la review humaine qui reste la garantie de qualité.

Mission 6

Qualification STAGING et mise à disposition recette · composants techniques

Palier 2 Palier 3 (PRA)

Pipeline lourd qui promeut l'image en RC, provisionne le RG STAGING iso-prod, exécute la batterie complète (DAST, charge, evals bloquantes RAGAS, PRA grandeur réelle), assemble le dossier MEP et pré-remplit le ticket EasyVista.

Objectif et fonctionnement

La Mission 6 est l'épreuve finale avant la production. C'est ici que l'on confronte l'application à un environnement qui est exactement équivalent à la PROD (mêmes SKUs, mêmes Azure Policies, mêmes Private Endpoints, même hub-peering) — d'où le terme "iso-prod" — et qu'on lui inflige une batterie de tests représentatifs des conditions de production.

Première action : promouvoir l'image de l'ACR. La même image binaire qui a été testée en DEV MVP est tagguée vX.Y.Z-rc (release candidate) dans l'ACR via un manifest copy — c'est une opération qui change le tag sans rebuild. La signature Cosign est attachée au digest, donc elle reste valide après le retaggage. Cette mécanique garantit que l'image testée en STAGING est cryptographiquement identique à celle qui ira en PROD.

Ensuite, M6 provisionne le RG STAGING via Terraform et y déploie l'image. La batterie de tests démarre :

  • DAST (OWASP ZAP) : scan dynamique de sécurité contre l'application qui tourne. Détecte les vulnérabilités exploitables côté HTTP (injection, XSS, authentification cassée, configuration TLS faible).
  • Tests de charge (Azure Load Testing) : simulation d'un trafic réaliste contre l'application. Vérifie que les objectifs SLO (latence P95, taux d'erreur, throughput) sont tenus sous charge.
  • Evals RAGAS bloquantes : pour les applications IA, mesure la qualité des réponses du LLM sur un jeu d'évaluation versionné. Trois métriques principales : faithfulness (la réponse est-elle fidèle aux sources ?), answer relevance (répond-elle à la question ?), context precision (la récupération RAG ramène-t-elle les bons documents ?). Seuil bloquant fixé à 0.85.
  • PRA scripté grandeur réelle : exercice automatisé de Plan de Reprise d'Activité. Le pipeline simule la perte de la région primaire et vérifie le basculement vers la région secondaire dans les délais cible (RTO et RPO).

Si tous les tests passent, M6 assemble le dossier MEP (équivalent du Conformité Finale mais pour la PROD) et crée automatiquement un ticket EasyVista pour demander la fenêtre de mise en production. Ce ticket est pré-rempli avec toutes les informations : version, fenêtre proposée, dossier en pièce jointe, contacts escalade. Il déclenche la Triple Approbation hors Azure DevOps (sponsor métier + CAB DPMSI + exploitation).

L'enjeu pédagogique : découvrir en STAGING les problèmes qui auraient été désastreux en PROD. Un test de charge raté en STAGING, c'est un retard d'un jour ; un test de charge raté en PROD, c'est une interruption de service.

Mission 7

Déploiement Production et supervision continue · composants techniques

Palier 2 Palier 3 (rollback auto)

Objectif et fonctionnement

La Mission 7 est l'aboutissement du parcours : mettre l'application en production avec un risque maîtrisé. La caractéristique clé est que la bascule n'est jamais brutale : on bascule progressivement le trafic de l'ancienne version vers la nouvelle, en vérifiant à chaque étape que tout va bien, et en revenant immédiatement en arrière au moindre signal d'alerte.

Première action : promouvoir l'image RC en version finale via un nouveau manifest copy dans l'ACR (vX.Y.Z-rc → vX.Y.Z). Toujours sans rebuild : c'est la même image cryptographique qui a été testée en STAGING.

Ensuite, M7 applique Terraform sur le RG PROD pour s'assurer que l'infrastructure cible est conforme. Puis elle déploie une nouvelle revision du Container App (la "verte") tout en gardant l'ancienne (la "bleue") active. Le mode multiple revisions des Container Apps permet de faire coexister les deux pendant la bascule.

La bascule progressive s'exécute en quatre paliers de trafic : 5%, 25%, 50%, 100%. À chaque palier :

  • Le pipeline pousse une fraction supplémentaire du trafic vers la revision verte
  • Il attend un délai de stabilisation (typiquement 5 à 15 minutes)
  • Il interroge Application Insights pour vérifier le SLI (latence P95, taux d'erreur)
  • Si le SLI est respecté → passage au palier suivant
  • Si le SLI dérape → déclenchement automatique de azp-rollback.yml qui ramène 100% du trafic sur la revision bleue, sans intervention humaine

Objectif de temps de rollback : moins de 5 minutes entre la détection de la dégradation et le retour à l'état antérieur.

Une fois 100% du trafic basculé et stable, M7 effectue les actions de clôture : inscription automatique dans la CMDB Digit-AI (l'application existe désormais officiellement en production), smoke tests post-bascule (vérifications de fumée que les fonctionnalités principales répondent), activation des règles Sentinel de drift (surveillance continue de la qualité des evals IA en PROD).

La revision bleue est conservée 24h avant d'être supprimée. Ce délai permet un rollback ultra-rapide si un problème est détecté après la bascule (le retour est instantané puisque les conteneurs sont déjà chauds).

L'enjeu pédagogique : la mise en production est devenue une opération sûre et réversible. Aucun MEP n'a la dimension dramatique des mises en production manuelles d'autrefois ; à la moindre alerte, le système se replie tout seul.

Workload Identity Federation · principe

Aucun secret partagé ni PAT n'est stocké dans Azure DevOps. Pour chaque Service Principal, une federated credential est créée dans Entra ID référençant l'organisation Azure DevOps, le projet et le pipeline. Au runtime, Azure DevOps émet un token OIDC consommé par Entra ID pour émettre un token Azure court terme.

Avantages opérationnels
  • Aucune rotation manuelle de secret pipeline
  • Aucun risque de fuite (pas de secret stocké)
  • Audit complet via les logs Entra ID
  • Révocation immédiate par suppression de la federated credential
Configuration type
  • Issuer : https://vstoken.dev.azure.com/{org-id}
  • Subject : sc://{org}/{project}/{service-connection}
  • Audience : api://AzureADTokenExchange
  • SP cible avec rôle RBAC scope minimum

Principe de routage Une alerte qui n'a pas de destinataire clairement responsable est une alerte qui sera ignorée. Chaque signal porte donc un ownership : si le diagnostic relève du code applicatif, c'est la Squad. Si le diagnostic relève de l'infrastructure ou du déploiement, c'est le Run. Archive logs anciens

Budgets et alertes

Quota par use case dédié au pipeline M4. Cap mensuel configuré. Évite qu'une remédiation en boucle infinie ne brûle le budget LLM. Métriques tokens consommés exposées au dashboard.

Dépendances structurantes entre composants

  • WIF OIDC avant tout : la totalité de la chaîne dépend de la configuration des federated credentials. Premier chantier du Palier 1 pour ne jamais avoir à recourir aux PAT.
  • ACR avant pipelines : la promotion manifest copy nécessite deux registries opérationnels avant même que M3 soit utilisable.
  • Standards versionnés avant audit : repo digitai-standards stabilisé avant la mise en service de M2.
  • Cosign avant admission policy : la verification policy en admission Container Apps suppose que toutes les images de l'ACR sont signées. Migration big-bang ou progressive selon l'inventaire existant.
  • Hub peering avant DEV MVP : sans hub-peering, le DEV MVP ne peut pas être iso-prod. Premier livrable d'infrastructure du Palier 1.
  • Log Analytics workspace par env avant Sentinel : Sentinel s'appuie sur un workspace consolidé par environnement, ces workspaces doivent exister avant l'activation de Sentinel.
  • EasyVista API key avant M6 : intégration ITSM négociée avec l'équipe EasyVista, secret stocké dans KV Platform, à finaliser au Palier 2.
  • AI Foundry workspace avant M4 Palier 3 : provisioning AI Foundry, content safety, quota dédié à valider au Palier 3.
Cap stratégique L'architecture cible peut être assemblée pièce par pièce sans rupture entre paliers. Aucune composante du Palier 1 n'est jetable au Palier 2 ni au Palier 3. La trajectoire 3-mois / 9-mois / 18-mois protège l'investissement et permet d'apporter de la valeur dès les premiers POCs traités tout en construisant progressivement la chaîne 0-touch cible.
